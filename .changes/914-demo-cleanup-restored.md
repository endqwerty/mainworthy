`mainworthy serve` again refreshes the demo after a deploy and deletes the retired one, both paused since 2026-10-24. The refresh seeds the demo inside the server's process, so it now also works behind a proxy that proves itself with `MAINWORTHY_PROXY_SECRET`, and no token is made for it or sent anywhere. Each cleanup slice now reads only the retired demo's own rows, by index, so its cost no longer grows with the other projects on the instance; a table owned through its parents, such as a run's slots, is read one batch of parents at a time, so a slice's cost no longer grows with the size of the demo either. On a copy with 20 projects and a million results, the longest slice fell from 289 ms to 27 ms and the whole cleanup from 140 s to 46 s. Migration 6 adds the indexes the cleanup reads by. When two instances share a database during a rollout, the second finds the first one's demo and keeps it, with the edits made in it, also when it lost the lock that keeps the two refreshes apart; a retired demo one of them already removed no longer stops the other's refresh; and a refresh that lost that lock while a newer revision replaced the demo has its next write refused, so it never adds its data to the newer demo. While two retired demos wait for a cleanup that keeps failing, a new revision retires no third: the demo keeps its earlier revision and the server logs why. On SIGTERM, `serve` stops its demo refresh, cleanup and work renewal at their next statement, and none of them commits. A statement waiting for another writer's lock waits on, so `serve` exits after 7 seconds at most, with a warning naming what was still running, inside the 10 seconds Cloud Run allows; PostgreSQL then rolls that statement's transaction back within about a second.
