- 2026-10-13: every reply carries security headers; before, only the documentation's did, and in local mode any page the owner visited could show the signed-in workbench in a frame. The web UI's page runs under `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, with no `'unsafe-inline'` and no `'unsafe-eval'`; every other reply (the API, the change stream, archives, `/mcp`, errors, the UI's script and style sheet) carries `default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. All carry `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin` over https and on this machine's own names (a browser ignores it elsewhere), and `Strict-Transport-Security: max-age=31536000` when the request came over https (by its scheme or the first element of `X-Forwarded-Proto`). The 500 reply is written without the request, so it carries neither of those two. **Changed:** the app can no longer be shown in a frame, by any page; the UI's script, style sheet and icon are sent with `Cache-Control: public, max-age=31536000, immutable` and the page with `no-cache` (the executable sent neither); a request to a path of the web UI with a method other than GET or HEAD is answered 405, where the executable answered with the page. A start from source without `NODE_ENV=production` serves Bun's development bundle under the same policy plus three things that bundle needs: the hash of Bun's one inline script, `blob:` scripts for hot reload, and inline styles for the error Bun shows in the page. That bundle's reload socket opens only for the server's own page: another site's page, a page on another port of the same machine and a name that is not this machine's are answered 403 (the reply that opens the socket, a 101, is the one reply with no security headers: a browser applies none to a socket). The documentation at `/docs` keeps the policy of its own pages and its `Referrer-Policy: same-origin` (a page frames its diagrams, so its framing header is `SAMEORIGIN`) and gets the other headers. What each header is for and how the UI's files come to carry them: `docs/architecture.md`, "What every reply carries".
- 2026-10-13: **Changed:** a browser's session is not the token (issue #88 item 3, decision 0017). Signing in opens a session and gives the browser a cookie of 32 random bytes, `__Host-mainworthy_sid` over https and `mainworthy_sid` over plain http; the server stores only its SHA-256. Before, the cookie held the token itself for a year, and signing out ended nothing. A session ends at `POST /api/logout` (a copy of the cookie stops working with it), after 14 days without use, after 90 days in any case, when the token that opened it is revoked and when its actor is forgotten. `MAINWORTHY_SESSION_IDLE` and `MAINWORTHY_SESSION_MAX` change the two lifetimes (`12h`, `14d`, `2w`); a value that is not a duration stops the start. **What breaks:** every browser is signed out by the upgrade and signs in again with a token; the cookie `mainworthy_session` is no longer read, and a sign-in removes it. Tokens are unchanged for scripts, pipelines and agents. The database gains the table `sessions` (schema version 2, with a copy of the database written beside it first); an archive exported before still imports, because an archive now names the version of what it holds and not the schema's. How to upgrade: `docs/deploy.md`, "The upgrade to sessions".
- 2026-10-13: a token that only reads shows when it was last used. Every request that is let in notes the use in memory, and the server writes the notes once a minute and when it stops, so a read never waits for the writer. Before, `last_used_at` was written after a write only. `token.list` shows a use at once. A stop that is not graceful loses the notes since the last write.
- 2026-10-13: a read that a reader thread starts after its caller's session ended, token was revoked or actor was forgotten is answered 401 with no data. Before, a read handed to a busy reader was answered with the caller as it stood when the read was dispatched.
- 2026-10-13: a token can have an end (issue #88 item 4, decision 0017). `mainworthy token new --expires 90d`, `expires` on `token.create` and "Expires" in Settings (never, 30 days, 90 days, 1 year) give a token a lifetime: a whole number and `h`, `d` or `w`. From its end on, the token is refused exactly as a revoked one is, and every browser session opened with it ends with it. Before, a token worked until somebody revoked it. `mainworthy token list`, `token.list` and Settings show when each token ends (`expiresAt`, `expired`), who made it (`createdBy`) and the address it was last used from (`lastUsedFrom`). Each start names, in one line on stderr, every token that ends within 14 days. `docs/deploy.md` says how to replace a pipeline's token with no gap.
- 2026-10-13: **Changed:** a new value in `MAINWORTHY_OWNER_TOKEN` retires the old one (issue #88 item 2). When the variable holds a value that is not yet a token, the start revokes every token that came from the variable and still works, whoever was the owner when it was set, which ends the sessions opened with them. One line names each token and its actor. So a start that changes `MAINWORTHY_OWNER` and the token together retires the earlier value too. Before, both values worked for good, so replacing a leaked value stopped nothing. A value that is already a token retires nothing. A token the owner made by hand, and one a start generated, are not touched, with one exception: the upgrade marks every token whose label starts with `owner (from ` as coming from the variable, so a token made by hand with such a label before the upgrade is retired with the rest. A configured value that is a token past its end is now said at the start, with the time it ended, as a revoked one already was; it is not brought back.
- 2026-10-13: **Changed, and it can stop your start:** `MAINWORTHY_OWNER_TOKEN` shorter than 20 characters or longer than 512 stops the server, in local mode too, with a line that says how to make one (`openssl rand -hex 32`). One shorter than 32 starts, and every start warns. Check the value before you deploy this build. 512 is also the longest token `POST /api/login` reads, so a configured token can always sign a browser in; before, a token could be any length. `POST /api/login` no longer refuses a token shorter than 8 characters before looking at it. A start that is refused, for the token or for a `MAINWORTHY_OWNER` that is not a person's name, now says what is true: no actor and no token was changed, and the database may already have been brought to the build's schema, with a copy of it as it was beside it. Before, it said "nothing was changed". No token longer than 512 characters works any more, as a bearer or at sign-in: a longer owner token an earlier build accepted is refused, and a new value is the way back in.
- 2026-10-13: the server stores where a token and a session were used from (issue #88 item 5): the address of a token's last use, and the addresses a session was opened from and last used from. The address a session was opened from is written at sign-in. The address of a later use is noted in memory and written with the time of that use, in batches: normally within a minute, longer behind a long write. A session's addresses go with its row, 30 days after the row records its end, which for a session whose token was revoked is when the minute job marks it expired and not the moment it stopped working. A token's address stays with the token's row, which nothing deletes yet; forgetting the token's actor erases it at once. `docs/compliance.md` has the table. Before, no address was stored. The first start of this build adds the columns after writing `mainworthy.db.v2.bak`; tokens and sessions keep working, except a token longer than 512 characters, which no longer works at all.
- 2026-10-13: **Changed:** failed sign-ins are limited (issue #88 item 1, decision 0017). A wrong token, sent as a bearer token on a route that needs a sign-in or typed into the sign-in form, is counted against the address it came from and against its first 8 characters. A route that needs no sign-in (`/healthz`, the API description, the documentation) looks at no token, and a sign-in body the form does not accept (longer than 512 characters, or not text) is refused without being counted. The fifth failure of either within 15 minutes blocks it for one second, and each failure after that doubles the block, up to 15 minutes. A blocked request is answered `429` with `Retry-After` and the new error code `limited`, and its token does not decide the answer: one that is not in the form the server generates is not looked up at all. A right token the server generated passes all the same, so a pipeline is not stopped by whoever shares its address; passing does not end the block, which runs out by the clock. The token the server made from the value of `MAINWORTHY_OWNER_TOKEN` is one a person chose and gets no such pass, whatever it looks like (a generated token later copied into the variable is still the server's and passes). A session cookie is never counted; a request that also presents a token is judged by the token. The CLI prints `limited: too many failed attempts; try again in 4 seconds` and exits 4; the sign-in form says "Too many attempts. Try again in 4 seconds." Two new variables say which peer is the proxy in front and where it writes the visitor's address: `MAINWORTHY_TRUSTED_PROXY` (addresses and ranges) and `MAINWORTHY_CLIENT_ADDRESS_HEADER`. Set both or neither; one without the other, or an entry that is not an address or a range, stops the start with a line that says which. Without them a request from a loopback or private address, which is every request behind a proxy with such an address, is not counted by address, and a start in server mode says so in one line on stderr; a proxy with a public address is counted as one address, so its visitors share one count until the proxy is named. Before, a wrong token cost one request and nothing limited the next. **What breaks:** a reply's error code can be `limited`, a seventh code (the API description lists it); a script that keeps sending a wrong or revoked token is answered `429` instead of `401` once it has failed five times; a start in server mode that sets neither variable prints one more line on stderr. The instance at `mainworthy.com` does not set the two variables yet: `docs/deploy.md`, "The limit on failed sign-ins", says which values are expected there and how to check them.
- 2026-10-13: **people sign in as themselves** (issue #30, first slice; decision 0017): the server and the command line. An admin who is a person invites somebody with `mainworthy invite new <name> [--can read,answer] [--project <key>] [--expires 3d]`, which prints a link once (`<public address>/invite#<code>`; only the SHA-256 of the code is stored). The person accepts it with a password of 12 to 256 characters, a passkey, or both, and from then on signs in with their name and password or with the passkey. For a person who exists the link is a recovery, which the owner makes for anybody and an admin who is a person makes for themselves: accepted, it replaces every password and passkey the person had and ends their sessions. **New routes:** `POST /api/login` also takes `{ name, password }`, `{ passkey }` and `{ invitation, ... }`; `POST /api/login/challenge`; `GET /api/login/methods`; `POST /api/account/password`. A name, a password, a passkey's answer or an invitation code that is looked at and refused is answered the same whatever was wrong, and the reason is in the server's log as a code. **New operations:** `session` (list and end your browser sessions; an admin who is a person, anyone's), `credential` (list, register a passkey, remove one; the last stays) and `invitation` (create, list, revoke), each a command too. `GET /api/session` also says which session the request came by (`session`) and what the person signs in with (`credentials`). **New variable:** `MAINWORTHY_PUBLIC_URL`, the address people open the instance at. A passkey belongs to its host name, so one made there does not work at another name of the same instance; unset, there are no passkeys and a link has no host; a value no browser makes a passkey at stops the start, and so does one with a path or a query. **Changed:** `POST /api/login` refuses a body that holds a token and anything beside it, where it took the token before. The database moves to schema 4, with a copy written first. An archive still imports and holds no password, passkey or invitation: after an import the owner invites each person again. Forgetting a person also revokes their passwords and passkeys, erasing each hash and key, and their open invitations. A token still signs a browser in, and the owner's last token is still not revoked. The pages (sign-in, the invitation, "Your sessions", "Your sign-in") come with the web UI's pull request; until then these are routes and commands.
- 2026-10-13: a passkey ceremony is finished where it began (decision 0017, after an independent check). `POST /api/login/challenge` with `{}` now sets a cookie, `mainworthy_ceremony` (`__Host-mainworthy_ceremony` over https; `HttpOnly; SameSite=Strict; Path=/; Max-Age=300`), and `POST /api/login` with `{ passkey }` is refused without it; the reply to an answer that was looked at clears it. A browser sends it by itself; a script that signs in with a passkey has to keep it. A passkey registration (`credential` with `passkey.begin` and `passkey.add`) is finished by the browser session that began it and by no other session of the same person, and one begun for an invitation is accepted with that invitation only. **Changed:** a token no longer registers a passkey (`forbidden`), as it sets no password. A sign-in body the server cannot read (over 16 KiB, or not JSON) is answered `that did not sign you in`, where it said `a token is required`. Client data that begins with a byte-order mark is read by the routes as the verifier reads it; before, the verifier accepted it and the routes refused it.

- 2026-10-13: **`mainworthy seed <project>`** fills a new or empty project with demo data: a shop's 2000 cases (`--cases` sets the number), a pipeline's results on three commits with one failing test, a planned run on pull request 482, and an agent's finding and proposed edit. - 2026-10-13: web: **Changed:** Enter and Space press a button that was reached with the keyboard, and Enter follows a link reached that way, on every screen. Before, a screen's own binding on those keys took them, so a button reached with Tab could not be pressed on the Suite or in a run: "Sign out" was one. A button that was clicked with the mouse, until the focus moves on, and the rows of a screen's list still leave both keys to the screen.
- 2026-10-13: web: after a conflict is resolved in the card, the case shown and the editor that `e` opens are the version the merge made, or a later one (issue #94). Before, the page went on showing the version from before the merge until it had read the case again, a moment on a quick connection and longer on a slow one, and what was typed in that time was typed onto the colleague's text, as a draft on their version. The card now stays until the page has read the case: at the version the reply to the merge names, or as it is now when the merge made no version of its own. A second tab that shows the same draft does the same when the first tab resolves the conflict or records the draft: it keeps the draft and its card, read-only, until it has read the case, and then shows the case as the server recorded it. While it waits, the pane says that it is reading the case, where it said the case was being edited in another window. If the read fails, the card stays and the page says so. "Resolve conflict" reads again in the tab that sent the merge; `e` or "Read the case again" does in a second tab. A person who leaves the case in that second tab before it could be read sees it as the page last read it, and the editor does not open on that: `e`, or a click on a field, reads the case first and opens on what comes back, or says that the read failed and opens nothing. A new case's draft that another window recorded or ended is no longer announced as a resolved conflict.

- 2026-10-13: the owner can be renamed. Set `MAINWORTHY_OWNER` to the new name and the new variable `MAINWORTHY_OWNER_WAS` to the name the owner has now, and start again: the start renames that person and says so in one line. They keep their tokens, password, passkeys, sessions and history; a password is typed with the new name from then on, and a draft a browser kept under the old name is not shown to the new one. Before, a changed `MAINWORTHY_OWNER` could only make a second owner, and no name could be changed. The start is refused, and changes nothing, when `MAINWORTHY_OWNER_WAS` names nobody, an agent, a pipeline, a forgotten person or a person who does not hold every capability on every project (what every start gives the owner), and when the new name is not one a person can be given. Left set after the rename it renames nobody, and every start says to unset it. `compose.yaml` and `compose.coolify.yaml` pass the variable on. Nobody else's name can be changed. `docs/guide/configuration.md`, "Rename the owner".

- 2026-10-13: CI: the gate reads each shard's newest attempt (issue #124). A shard's report is uploaded as `results-<shard>-attempt-<n>` and each artifact is downloaded into its own directory.
