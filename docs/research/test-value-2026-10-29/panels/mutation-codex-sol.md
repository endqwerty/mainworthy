I recommend **(b), with a restricted part of (c)**, after the shared per-test facts read and findings exist. Mutation belongs in Mainworthy as optional, attributed evidence from a repository-side assessor. It should not become a required score, an execution service, or a condition for using test assessments. This is a product recommendation, not an implementation approval. The settled staged direction supports that boundary (`out/panel1/contrarian.md`; `out/panel1/codex-sol.md`).

1. Accept a supported version of mutation-testing-elements JSON through a registered evidence operation. Keep mutation observations separate from ordinary test executions and gates. Today's adapters expect execution results, so adding mutation statuses to `report` would conflate different records (`src/surfaces/formats/report.ts:9,62`). Require an envelope naming the commit, producer, tool configuration, sampled region, baseline outcome, and test-selection scope. Map report-local test IDs to Mainworthy test identities explicitly. Keep unmatched observations report-scoped, and expose them on linked cases only through their automated tests. Reads follow the module map; accepting a finding follows the Witness rule (`AGENTS.md:30-32`).

Start with the standard JSON, not separate vendor integrations. PIT can produce it through a plugin, so do not promise native compatibility with every PIT installation ([PIT plugin](https://github.com/Wmaarts/pitest-mutation-testing-elements-plugin)). Mainworthy neither runs source code nor calls an AI API. Execution infrastructure is already outside the product vision (`docs/product-vision.md:264-270`).

2. Show the user the mutation, source revision, reported status, mapped covering tests, reported killing tests, and unresolved identities. A per-test fact can say "reported killing test for these mutations at this commit". Preserve compilation failures, timeouts, and missing attribution separately. Do not convert them into assertion kills or zeros.

The decisive limitation is that the standard permits `killedBy` to contain just the first failing test after early termination. Coverage and test definitions are optional. One reported killer therefore does not establish a unique killer ([report schema](https://raw.githubusercontent.com/stryker-mutator/mutation-testing-elements/master/packages/report-schema/src/mutation-testing-report-schema.json), `killedBy`, `coveredBy`, `testFiles`; saved in `codex-sol-support/`). This corrects the research notes' implication that per-test coverage alone establishes the unique kill set (`out/research/literature.md`, section 2).

Allow **keep** only when an assessor supplies a reproducible baseline/mutant replay demonstrating a relevant catch. Say "only observed killer among the declared tests" only with complete comparable outcomes for that declared set. A surviving mutant supports investigation. Suggest **refactor: weak assertion** only after a replay and attributed review establish a meaningful reachable change that the intended assertion misses. Equivalent mutants, an uncovered branch, or an incomplete run do not establish that diagnosis. Snapshot this evidence in the finding. Neither zero kills nor a surviving mutant decides delete, merge, or move-down (`out/phase2/RESULT.md`, Method and What this cannot see; `out/panel1/codex-sol.md`, evidence gates).

The local experiment justifies accepting evidence: the cover kept 208 of 778 callbacks while losing kills m001 and m015 among 18 full-selection kills. But "full" meant baseline-covering tests, not every browser test. Eleven mutants survived those browser selections, four failed to build, and one timed out. This cost-filtered sample does not estimate future regression protection (`out/phase2/RESULT.md`; `out/phase2/mutants.csv`).

3. Users who already generate reports pay upload, mapping, storage, and review costs. Others must also maintain a mutation runner and investigate survivors. Embedded source makes standard reports more expensive to retain than summaries. No ingestion throughput, implementation effort, or storage volume has been measured here.

For compute planning, assume the observed approximately two-hour local experiment occupied one runner for 7,200 seconds. At the repository's dated private-Linux planning rate, that is $0.72 per execution, approximately $3.12/month weekly, or $3,261.60/month at 4,530 executions. Eight CPU threads are not eight separately billed runners. These are conditional proxies, not measured hosted-runner costs or this public repository's bill (`docs/development/tests.md:167-195`; `out/phase2/RESULT.md`; calculations and script in `codex-sol-support/`).

I propose no recurring mutation job for this repository now. Use targeted local mutation when evaluating a concrete assertion change or test removal. Test the new importer and inference boundaries with small deterministic fixtures in existing checks. Measure their added occupied job time before delivery; each added second on every run costs approximately $0.45/month under the planning baseline (`AGENTS.md:40-43`).

4. Reject orchestration, mandatory mutation thresholds, and default weekly browser mutation. The experiment is expensive, and the researched Bun runner declares a TypeScript incompatibility that remains untested here (`out/research/methods.md`, M6a). Documentation alone leaves useful evidence outside the shared read. Repository-only CI does not help product users. Competitor research establishes no mutation-ingestion advantage, and absence from its surveyed pages cannot prove competitors lack it (`out/research/competitors.md`).

5. The strongest objection is that generic findings with artifact links may deliver nearly all the value without a new importer. Identity mapping and incomplete killer attribution could consume more effort than users save. The Java study's 17% uncoupled real faults is a study result, not an upper bound on missed faults in this TypeScript UI (`out/research/literature.md`, section 2). If the shared finding workflow sees no real mutation-report use, defer the importer and retain that generic workflow.
