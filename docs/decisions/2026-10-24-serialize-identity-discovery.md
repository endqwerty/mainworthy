# Serialize identity discovery and mutation

- Date: 2026-10-24
- Status: accepted
- Issue: https://github.com/endqwerty/mainworthy/issues/821

Actor footprint discovery followed by later rechecks failed three contention reviews. A name can disappear while actor locking waits, and an id can first become visible after the last check. Both permit an operation to take an earlier actor or organisation lock after a project lock. Real PostgreSQL regression tests reproduce deadlocks for token creation, invitation creation, token revocation, credential removal, and session ending.

Identity writes now acquire one transaction advisory lock before discovery and all actor or project locks. This revises the no-shared-authority-lock choice in the PostgreSQL decision of 2026-10-23. The registry takes it for every instance write. Direct identity mutation entry points use the same lock. Project data writes keep shared actor locks and project row locks, and never join it. Footprint discovery still acquires affected actors before projects because data writers can hold an actor while waiting for a project. The registry's organisation-row absence reservations and post-wait footprint checks are removed.

Per-name advisory reservations plus mandatory checked resolvers could retain concurrent identity writes. That would require every name and id resolution to carry checked state across the identity module. Serialization instead keeps discovered identity owners stable until the transaction ends. A missing session id is handled separately below, since sign-in can insert it without changing its actor. Its cost is that one identity writer waiting on a busy project queues other identity mutations, including token creation. Expensive proof verification stays outside the lock. The concurrency document records the measured cost and the regression tests preserve ordinary project concurrency. Revisit this choice if that identity queue becomes a practical limit.

On 2026-10-25, contention review reproduced foreign-key deadlocks in run assignment and proposal adoption: the project writer holds its project and needs `FOR KEY SHARE` on another actor, while a grant change holds that actor `FOR UPDATE` and waits for the project. Authority locks, including the database trigger, now use `FOR NO KEY UPDATE`. It still excludes another authority change and a writer's `FOR SHARE` authority read, but permits foreign-key references. Actor-id updates are not an application operation. Archive deletion keeps its exclusive actor table lock before projects. Forgetting and owner renaming can implicitly take stronger name-key locks: registry forgetting already holds all projects before renaming, and bootstrap/direct forgetting do not acquire project locks after renaming.

Single-actor sign-in is outside identity serialization. Token sign-in shares its existing actor; credential sign-in takes that actor `FOR NO KEY UPDATE`, rereads its proof, and refuses any newly resolved owner. Credential use/counter updates never join the identity mutex after taking that actor. Sign-in neither changes actor membership/names nor locks projects. Session creation does not fire the authority-change trigger. Session ending rejects an id absent at discovery, so a concurrently created session cannot make it lock an undiscovered actor later. Invitation acceptance and identity linking remain serialized because they create or change identity. Real-connection regressions cover assignment, adoption, placement, the trigger and the late-session window. The updated benchmark shows unrelated token sign-in finishes before report release in all five queued samples, while token creation still waits. Same-actor contention and the identity-mutation queue remain.
